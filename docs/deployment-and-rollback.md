# Deployment and rollback

Before first deployment, verify that the production server root filesystem has at least 20 GB available with `df -h /`. `scripts/preflight.sh` enforces the available-space threshold and also verifies Docker, Compose, secret presence, permissions, and Compose validity.

The release workflow builds an immutable SHA-tagged image, publishes provenance and an SBOM, then deploys the build output by its `ghcr.io/<repository>@sha256:<digest>` reference. Staging and production check out `RELEASE_SHA`, archive only `compose.yaml`, `scripts/`, and the static Nginx configuration from that commit, and stage them into a new host release directory before invoking that staged commit's `scripts/deploy.sh`. The host's `.env`, `secrets/`, and active-slot configuration remain host-managed runtime state and are never transferred from CI. Configure required reviewers on the GitHub `production` environment. Workflow concurrency and the host `flock` prevent overlapping releases.

On the host, use `APP_IMAGE=ghcr.io/<repository>@sha256:<digest> scripts/deploy.sh`. Registry deployments reject tags and malformed digest references, force a registry pull, and verify that exact digest before starting the inactive slot. Use `--dry-run` to inspect actions. Manual direct-image use is deliberately separate: set `ALLOW_LOCAL_APP_IMAGE=1` and provide an already-present local `APP_IMAGE`; otherwise, a local tag never suppresses a registry pull. The script preserves the active slot until the inactive web and worker start, web health passes, shadow traffic succeeds, and Alembic succeeds. It switches Nginx, checks public application health, restores the old route on failure, and leaves both slots running so the previous slot remains rollback-ready until an explicit later cleanup.

Use `scripts/rollback.sh --dry-run` before `scripts/rollback.sh`. Rollback requires the previous slot to remain healthy. A failed or backward-incompatible database migration is not automatically downgraded; restore compatibility with a forward migration or perform the rehearsed database restore procedure. Never run `docker compose down`, delete volumes, or prune images during rollback.

If deploy fails before switching, inspect the inactive slot and migration output while production remains on the active slot. If health fails after switching, verify the automatic route restoration. If the deployment lock is held, identify the running workflow or process instead of deleting the lock file.
